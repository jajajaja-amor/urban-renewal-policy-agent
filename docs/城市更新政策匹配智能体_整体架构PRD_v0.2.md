# 城市更新政策匹配智能体｜整体架构 PRD v0.2

**状态：** 产品定义讨论稿，尚非开发验收定稿  
**范围：** 第一阶段 MVP 的用户端政策研判流程；国家政策与北京市政策  
**方法参考：** 用户提供的《AI产品的PRD和UE设计》课件，采用“目标—边界—行为—指令—知识—工具—异常—验收”的 AI PRD 骨架。课件中的客服实例、指标和技术选型均不作为本项目事实。  
**依据标记：** 【已确认】来自用户需求及此前认可的产品定位；【设计建议】用于讨论的实现方案；【待定】需进一步决策。

## 0. 本版相对 v0.1 的修正

v0.1 主要描述了流程与角色，缺少可用于评审的**场景行为、UE 状态、资料责任、工具权限和验收口径**。本版补齐这些章节。完整节点 Prompt、字段字典、评分公式和技术架构仍需后续单独定义，避免在总体架构阶段假装已经确定。

## 1. 背景、用户与目标

### 1.1 用户问题【已确认】

设计师和甲方业务团队需要从项目任务书或投标文件中判断项目的城市更新属性，理解国家及北京政策的具体条款，研究申报方向，并寻找同地区同类型案例。难点在于政策细节和对标案例的分析研判。

### 1.2 产品目标【已确认】

让用户从一份项目材料出发，得到**有来源、能核对、能指导下一步工作的政策研判**：项目如何定性、哪些政策相关、关键条件是否满足、优先关注什么方向、哪些北京案例可以对标。

### 1.3 MVP 成功的可观察结果【设计建议】

用户完成一次上传和必要的事实核对后，可以：

1. 看懂系统提取的项目画像，并纠正错误；
2. 查看每项政策推荐对应的项目事实和政策原文；
3. 分清“方向相关”“条件待核”“可进一步研究申报”三类表述；
4. 明确下一步需要核实的信息或准备的材料；
5. 理解案例的相似点、差异点与借鉴价值。

目前**不设定**准确率、耗时、政策覆盖率等数值目标；这些指标及门槛需在确定样例项目、资料范围和评估方法后制定。

### 1.4 版本范围

| 第一阶段 MVP【已确认方向】 | 第二阶段【已确认方向】 |
|---|---|
| 项目上传、项目画像、国家及北京政策匹配、分级建议、北京案例分析 | 评估接入现有的政策匹配与结构化入库探索工作流，完善政策自动采集与更新 |

首批文化类城市更新项目的细分类型、资料覆盖边界和实际运行平台【待定】。

## 2. 能力边界

| 系统可以做【已确认/设计建议】 | 系统不能直接做【边界】 | 越界时的行为 |
|---|---|---|
| 提取项目事实、关键词和待核信息 | 把未出现于材料中的项目事实写成已证实事实 | 标为“待核实”，请用户补充 |
| 检索、比较国家和北京政策 | 仅凭关键词命中就判定政策适用 | 展示候选及其待核条件 |
| 解释政策关联、建议关注方向 | 承诺申报资格、获批或资金结果 | 使用“建议进一步核实/研究”的表述 |
| 分析北京案例及检索关键词 | 把案例做法直接视为当前项目可复制方案 | 指出项目条件差异 |
| 生成研判报告 | 伪造政策条款、案例来源、文件时效 | 缺少可靠来源时不输出肯定结论 |

**重要口径：** 政策关联度、适用条件状态、建议优先级分别输出。关联度高不自动表示符合申报条件。项目与政策的数字评分是否使用及如何计算【待定】。

## 3. 用户流程与 UE 状态

| 页面/状态【设计建议】 | 用户输入或动作 | 系统可见反馈 | 下一步 |
|---|---|---|---|
| 任务创建 | 上传任务书、投标文件或项目说明；填写项目名称 | 显示文件接收和解析状态；说明可分析的任务范围 | 进入项目画像 |
| 项目画像待确认 | 修改地点、更新对象、内容、主体、阶段等提取结果 | 每个字段显示来源或“用户补充”；缺失项显式提示 | 用户确认后发起研判 |
| 研判进行中 | 等待，或返回查看已确认信息 | 展示“检索政策/核验条件/比较案例”等进度状态；具体呈现方式【待定】 | 查看结果 |
| 结果总览 | 选择政策、申报方向或案例卡片 | 显示项目定位、政策分级、待核问题和建议行动 | 进入详情或修订 |
| 依据详情 | 点击政策或案例来源 | 显示原文出处、用于判断的内容及项目事实 | 返回总览 |
| 修订与反馈 | 更正项目事实、指出结论问题 | 标明需要重新研判的内容；保留修订来源 | 更新结果 |
| 无法判断 | 补充资料或暂停研判 | 明确缺少什么，以及目前能给出的有限结论 | 补充后继续 |

**交互原则【设计建议】：** 引导上传和补充信息；等待时显示真实处理阶段；关键结论可追溯；允许更正；不确定性直接呈现。第一阶段是否配置人工专家接管渠道【待定】，因此不承诺自动“转人工”。

## 4. Agent 行为定义

| 场景 | 期望行为 | 不可接受的行为 |
|---|---|---|
| 材料信息完整 | 提取事实、展示出处，供用户确认后继续 | 跳过用户核对直接定性 |
| 任务书中缺少主体、阶段或资金信息 | 标记缺口；只在确实影响判断时追问 | 猜测主体或资金并继续给确定结论 |
| 用户更正项目画像 | 使用更正后的事实重新判断受影响结论，标明用户补充来源 | 继续引用已被更正的旧事实 |
| 搜索得到多条同名或相近政策 | 核对发布机关、地区、日期和原文，保留可验证候选 | 仅凭摘要或标题合并为一条政策 |
| 政策方向相关但申报主体不明或条件不满足 | 分别呈现方向关联与资格条件，并说明缺口或不符点 | 输出“可直接申报” |
| 政策已过期、疑似被替代或时效不明 | 标明时效状态；未经核实不作为当前申报依据 | 将旧政策当作现行政策推荐 |
| 没有足够北京同类案例 | 明示案例覆盖不足，可给检索关键词 | 编造案例或无依据地声称“同类成功案例” |
| 政策条款与模型生成结论冲突 | 退回核验，仍无法消除冲突则显示待核 | 用流畅措辞掩盖冲突 |

## 5. 工作流与 Prompt 规格

### 5.1 主工作流【设计建议】

```text
文件接收与解析 → 项目事实提取 → 信息完整性判断 → 用户确认项目画像
   ├→ 国家/北京政策候选检索 → 条件核验与分级 ─┐
   └→ 北京案例候选检索     → 相似与差异分析 ─┤
                                                 ↓
                                         建议与报告生成
                                                 ↓
                                         来源和结论核查 → 展示
```

### 5.2 角色与交接【设计建议】

第一阶段以**一个主工作流**协调职责，不预设多智能体自治。逻辑角色如下：

| 角色/节点组 | 输入 | 输出 | 权限边界 |
|---|---|---|---|
| 项目分析 | 解析后的用户材料 | 结构化项目画像、出处、缺失项 | 不能补造项目事实 |
| 检索规划 | 用户确认的项目画像 | 政策与案例检索条件 | 不能判定检索命中即适用 |
| 政策研判 | 项目画像、政策原文和来源 | 关联理由、条件状态、优先级建议 | 不能承诺申报结果 |
| 案例分析 | 项目画像、案例材料和来源 | 相似点、差异点、借鉴点、关键词 | 不能臆测案例因果 |
| 报告与核查 | 以上结构化结果 | 面向用户的报告、待核问题 | 不能新增无来源事实 |

### 5.3 Prompt 文档要求【设计建议】

完整 Prompt 在节点规格阶段编写并版本化。每个节点至少记录：目标、允许使用的资料、输入变量、输出结构、事实与推断标记、禁止行为、缺失信息处理、示例和版本。上传文件和网页内容一律作为**待分析资料**，不能改变系统指令或角色权限。单纯字段校验、条件分支和结果汇总由确定性逻辑处理；模型用于材料理解、语义比较和解释。

## 6. 知识与数据

| 数据对象 | 第一阶段拟定来源 | 使用要求 | 尚待确定 |
|---|---|---|---|
| 项目材料 | 用户上传及用户补充 | 保留字段出处；区分原文、补充与推断 | 文件格式、存储期限、权限 |
| 国家及北京政策 | 官方发布的政策原文【设计建议】 | 保存标题、发布机关、时间、地区、链接、条款和时效核验结果 | 首批清单、维护人、更新周期 |
| 北京项目案例 | 可核实的官方或项目公开资料【设计建议】 | 保存项目位置、类型、措施、出处；效果或资金信息须有证据 | 首批案例范围与审核责任 |

现有政策采集和结构化入库工作流为第二阶段可评估资产。工作区已有探索流程说明，但第一阶段不能据此声称知识库会自动更新，或仅凭模型判断政策“真实性”。

## 7. 工具、接口与权限

本版定义**能力接口**，不指定 Coze、Dify、数据库或模型厂商。

| 能力接口【设计建议】 | 何时调用 | 最小输入 → 输出 | 操作性质 |
|---|---|---|---|
| 文档解析 | 用户上传后 | 文件 → 可定位的文本片段/解析错误 | 读取 |
| 政策检索 | 项目画像确认后 | 地区、类型、关键词 → 候选政策及来源 | 读取 |
| 案例检索 | 项目画像确认后 | 地区、类型、关键词 → 候选案例及来源 | 读取 |
| 原文读取 | 候选需要核验时 | 来源标识 → 政策条款或案例内容 | 读取 |
| 结果保存/导出 | 用户发起时 | 本次研判结果 → 可回看的结果或文件 | 写入；保存范围【待定】 |

第一阶段 Agent 不具有向正式政策库写入、修改原始项目材料、提交申报或对外发布结论的自主权限。具体 API 参数与权限方案在技术设计中确定。

## 8. 异常与降级

| 异常 | 用户可见处理【设计建议】 | 系统处理 |
|---|---|---|
| 文件损坏或无法解析 | 告知无法解析，允许重新上传或手工输入概要 | 停止依赖该文件的事实提取 |
| 关键项目事实不足 | 指明缺项及其影响 | 保留“待核实”，限制后续肯定结论 |
| 政策或案例检索无结果 | 告知覆盖不足，不展示虚构结果 | 保留查询条件，允许调整或稍后补充资料 |
| 来源不可访问或仅有搜索摘要 | 显示“原文待核” | 不将摘要当作正式条款依据 |
| 政策间冲突、时效不明 | 展示冲突和来源，提示进一步核实 | 不自动选定唯一正确政策 |
| 模型输出不符合结构或引用缺失 | 显示处理失败或有限结果 | 允许有限重试；持续失败则终止该结论 |

重试次数、超时、人工复核责任人及是否有人工接管服务【待定】。

## 9. 评估与验收设计

用户此前要求先完成架构，**本阶段不执行测试**。但 PRD 必须先定义未来如何判断产品是否可靠。

| 待评估维度 | 判断问题 | 门槛状态 |
|---|---|---|
| 项目事实提取 | 是否遗漏关键事实、是否把推断当事实、出处是否正确 | 待建立项目样例与专家标注后确定 |
| 政策召回 | 关键国家和北京政策是否被找出 | 待建立核验政策集后确定 |
| 条件核验 | 地区、主体、时效及排除条件是否判断正确 | 待建立规则口径后确定 |
| 依据可信 | 推荐结论能否回到正确的政策原文或案例来源 | 待确定抽检方式后确定 |
| 行动可用 | 设计师和甲方是否能据此决定下一步核实与研究事项 | 待确定用户评审方式后确定 |
| 异常处理 | 无资料、冲突、超范围时是否避免肯定性误导 | 待建立异常样例后确定 |

**上线判定原则【设计建议】：** 未经核实的政策资格结论、伪造来源或把过期政策作为现行申报依据，应视为严重错误。具体指标数值、样本量和上线门槛【待定】；不照搬课件中的客服指标。

## 10. 待决策与下一步产物

1. 选定首个文化类城市更新细分场景和一份可脱敏的真实任务书。
2. 定义项目画像字段、必填信息及追问条件。
3. 确定第一阶段政策与案例的起始资料范围和审核责任。
4. 决定是否显示数值匹配分、如何解释分数，以及与条件状态如何区分。
5. 决定用户界面平台、报告导出方式和是否需要人工接管。

这些决策明确后，依次形成**项目画像字段字典 → 节点输入输出与分支规格 → 逐节点 Prompt 文档 → UE 页面与状态稿 → Vibe Coding 实现提示词**。以上产物使用同一套业务口径和字段名称。
